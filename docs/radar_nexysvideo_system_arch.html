这次真正修掉的硬件问题

初始阶段最致命的 bug 并不是 cache，而是 MM2S 发起 DDR 读之后，返回响应在 MIG wrapper 这一层发生了 ID 宽度不匹配。

  • MIG 黑盒只有 4-bit AXI ID。
  • 共享 xbar 上一度长成了更宽的内部 ID，返回路径因此可能错路由。
  • 这会表现成 MM2S_LENGTH 一写下去就立刻报错，早期还伴随 a5a5... 污染读回。
  • 修复后，老的“启动即炸”故障消失，MM2S/S2MM 主链路恢复正常。
所以从硬件角度说，DDR 读返回路由问题已经被明确修掉，这一步是这次 bring-up 的真正硬件收口点。
后续才暴露出的软件约束

在硬件问题修掉之后，剩下的 `word 32` 错误并不是 DMA 又坏了，而是 CPU 和 DMA 共享了同一片 cacheable DDR。

  • Rocket D$ 是 4 KiB，cache line 是 64 B。
  • DMA 不和 Rocket D$ 自动保持 coherent。
  • CPU 写 TX buffer 后，如果不做 cache maintenance，DMA 可能从 DDR 读到旧值。
  • DMA 写 RX buffer 后，如果 CPU 不做 cache maintenance，再比较时也可能读到 cache 里的旧数据。
当前系统已经跑通，但它的系统约束是：CPU 与 DMA 共享 cacheable buffer 时，软件必须显式做 cache maintenance，或者未来引入真正的 coherence/uncached 方案。

如果你后面要继续扩展，这页最值得记住的几点
  • DMA 控制链和数据链现在都已经能板级跑通，后续扩展更应该关注“系统一致性”和“软件协议”，不只是硬件连线。
  • 只要 buffer 还在 Rocket 眼里是 cacheable DDR，CPU 与 DMA 共享它时就要考虑 flush / invalidate / eviction。
  • 如果以后要做更像产品级的数据通路，建议尽早决定是走“软件维护 cache”，还是走“uncached buffer / coherent fabric / dedicated DMA memory region”。
  • 这套架构已经足以作为下一阶段更复杂 stream 处理或雷达前端数据搬运的基础版本。
