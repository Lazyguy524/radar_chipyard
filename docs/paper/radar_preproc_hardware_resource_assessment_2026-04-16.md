# 雷达前处理上板资源余量评估

日期：2026-04-16  
对象：当前 `RadarAXIMMIONexysVideoConfig` / Nexys Video / `xc7a200tsbg484-1`  
参考 bitstream：`545-qmlp-wordbank-refactor-k7-2026-04-15.bit`

## 1. 当前资源基线

最新通过 bitstream 的全设计资源如下：

| 资源 | 当前使用 | 器件总量 | 估算占比 |
|---|---:|---:|---:|
| LUT | 28366 | 134600 | 约 21.1% |
| FF | 17445 | 269200 | 约 6.5% |
| RAMB36 | 2 | 365 | 约 0.5% |
| RAMB18 | 14 | 730 | 约 1.9% |
| DSP | 10 | 740 | 约 1.4% |

当前 QMLP 层级资源：

| 资源 | 当前使用 |
|---|---:|
| LUT | 3341 |
| FF | 1491 |
| BRAM | 0 |
| DSP | 0 |

当前主时钟 post-route timing：

```text
WNS = 0.531 ns
TNS = 0.000 ns
```

结论：从资源容量看，当前 FPGA 还有较大余量；从时序看，仍有正余量，但新增模块后需要重新做 timing closure。

## 2. 能否容纳数据前处理模块

总体判断：可以容纳轻量到中等规模的数据前处理模块，但不建议一次性把完整复杂前处理全塞进去。

### 2.1 轻量前处理：资源足够，风险较低

适合放到 FPGA 的内容：

- `x/y/doppler/rcs` 字段解包
- 固定窗口计数
- 求和、最大值、最小值
- 简单均值或用定点乘法近似的归一化
- INT8 量化、clamp、pack
- 生成 `int8[21]`
- `AXI-Stream feature21 -> QMLP` 串接

这类模块预计资源量通常可控制在：

| 资源 | 粗略估计 |
|---|---:|
| LUT | 1k 到 5k |
| FF | 1k 到 4k |
| DSP | 0 到 8 |
| BRAM | 0 到 2 个 RAMB36 等价 |

当前资源余量足够。

### 2.2 中等前处理：大概率装得下，但要小步验证

如果前处理包含：

- k 帧窗口缓存
- 多个点/目标的统计特征
- 多路并行累加器
- 若干定点乘法
- 少量除法近似或查表
- 简单状态机调度

预计仍然可以放下，但需要注意：

- 不要在一个周期内做过宽组合逻辑。
- 除法、开方、距离计算尽量用查表、迭代或流水线。
- 建议先做独立 OOC synthesis，再接入完整 SoC。
- 接入 AXI DMA / AXI-Stream 后再跑完整 bitstream。

### 2.3 复杂前处理：资源可能够，论文时间风险高

如果前处理实际包含：

- 动态点数聚类
- 排序 / top-k / 最近邻
- 复杂距离矩阵
- 浮点或高精度除法
- 大量随机访存
- 接近完整雷达信号处理链路，例如 FFT / CFAR / tracking

则不能只看资源余量。虽然 `xc7a200t` 的 DSP、BRAM 资源仍然很充足，但这类模块的主要风险会变成：

- 算法边界不清
- 数据格式不稳定
- 状态机复杂
- 验证样本不足
- timing 难收敛
- 论文周期内难以闭环

## 3. 当前最推荐的新增模块边界

建议先不要做“完整雷达前处理”，而是做一个边界清晰的：

```text
RadarFeature21Preprocessor
```

建议输入：

```text
AXI-Stream packed x/y/doppler/rcs 或软件侧定义的点级定点字段
```

建议输出：

```text
int8[21]
```

然后接入当前 QMLP：

```text
DDR / DMA
  -> RadarFeature21Preprocessor
  -> RadarAXISQMLP
  -> DMA / DDR
```

这样可以把论文主线从“只加速 QMLP”推进到：

```text
前级特征构建部分硬件化 + 后级 QMLP 分类器硬件化 + RISC-V SoC 数据通路闭环
```

这个方向比盲目继续优化 QMLP 更有论文价值。

## 4. 对当前资源余量的最终判断

当前硬件空间是够的。

更准确地说：

1. **资源够**：LUT 只用约 21%，FF 只用约 6.5%，BRAM 和 DSP 基本没怎么用。
2. **轻量 feature21 前处理非常可行**：特别是统计、量化、打包、固定窗口处理。
3. **完整复杂前处理不建议直接上**：不是因为装不下，而是因为算法、验证、时序和论文周期风险高。
4. **真正瓶颈不是资源，而是定义清楚前处理输入/输出和 golden**。

## 5. 下一步需要的软件侧资料

若要真正实现前处理硬件化，需要软件侧提供：

1. `x/y/doppler/rcs` 的定点输入格式。
2. k 帧融合的精确定义，当前 k=7 时每一帧如何参与。
3. 21 维特征的逐项公式。
4. 每个特征的量化 scale / zero-point / clamp 规则。
5. 至少 1000 组 `raw or point-level input -> int8[21]` golden。
6. 异常输入和边界输入样本。
7. 当前软件前处理的 CPU-only latency。

拿到这些后，才适合判断是否做完整 `RadarFeature21Preprocessor`，还是只做其中最耗时的 3 到 5 个统计特征。
