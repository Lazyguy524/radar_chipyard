# 《基于RISC-V的雷达信号智能处理系统设计与研究》硬件侧论文框架梳理

更新时间：2026-04-14

## 1. 文档目的与边界

本文档不是论文正文，也不是代码说明，而是面向硕士论文写作前期，用于梳理当前工程中**硬件实现部分**的主线、工作量、创新点候选和章节组织方式。

本文档只讨论硬件相关内容，包括：

- 基于 `RISC-V` 的 SoC 平台搭建
- `DDR + DMA + AXI-Stream` 数据通路
- 冻结模型 `21 -> 64 -> 32 -> 2 INT8 QMLP` 的硬件化实现
- `4-lane PE` 阵列化与相关优化
- 板级验证与时延结果

截至 `2026-04-14`，硬件侧最新有效模型基线已经更新为软件侧推荐的 `k=7 + rcs21` 版本。该版本仍保持 `21 -> 64 -> 32 -> 2` 矩阵维度与 `4-lane PE` 结构不变，主要替换权重、scale、requant multiplier 和 golden 数据，并已完成 `1000` 组大样本与 `54` 组边界样本板级对拍。

本文档不负责整理：

- 数据集构建
- 软件模型训练
- 算法精度对比
- 软件侧理论分析

这些部分应由软件模型主线另行展开。

## 2. 当前硬件侧已完成工作的系统归纳

从当前工程实现看，硬件侧已经不再是“单个加速 IP 的试验”，而是形成了一个较完整的雷达智能处理 SoC 原型。可以归纳为四层。

### 2.1 SoC 平台层

当前已经在 `Nexys Video + Chipyard` 平台上完成了基于 `Rocket RISC-V` 的 SoC 搭建，主要包括：

- 单核 `Rocket RV64` 软核 CPU
- `TileLink / AXI` 互连
- `DDR + MIG` 外部存储
- `AXI DMA`
- `UART-TSI` bring-up 链路

这部分的作用不是单独追求 CPU 性能，而是为后续雷达数据搬运、加速器挂接和板级运行提供一个可控的 `RISC-V SoC` 基座。

### 2.2 数据通路层

当前工程已经把主数据通路固定为：

`DDR -> MM2S -> AXI-Stream block -> S2MM -> DDR`

在这个框架里：

- CPU 负责控制与调度
- DMA 负责主存与流接口之间的数据搬运
- AXI-Stream 中间插槽负责承载算法相关硬件模块

这条数据通路先后承载了：

- `RadarAXISPreprocessor`
- `RadarAXISQMLP`

因此，当前工作不是“从零做一个加速器”，而是先完成了**系统级可复用数据通路**，再在其上逐步挂接算法模块。

### 2.3 模型硬件化层

当前已经完成冻结模型：

- `21 -> 64 -> 32 -> 2 INT8 QMLP`

的硬件化实现，对应模块为：

- [RadarQMLP.scala](/home/soooarr/chipyard/fpga/src/main/scala/nexysvideo/RadarQMLP.scala)

该模块的特点是：

- 输入维度固定
- 网络层数固定
- 权重和偏置来自 release 参数文件
- 输出为最终 `INT32 logits`

当前最新 `k7 + rcs21` 版本中，最终 `logits_int32[2]` 的类别含义为：

- `logits[0] -> pedestrian`
- `logits[1] -> vehicle`

硬件侧不做 softmax，仅输出两个定点 logits，最终分类可由 CPU 侧通过 `argmax` 完成。

这部分已经完成：

- 模型参数读取与硬件 elaboration 对接
- QMLP CSR 页扩展
- 与 `AXI DMA` 的流式集成
- 板级多样本对拍

### 2.4 优化与验证层

在固定模型硬件化跑通后，后续又完成了两条优化线：

1. **QMLP kernel 优化**
- 从 baseline `3554 cycles`
- 优化到 `v2.5` 的 `1301 cycles`
- 保留 `4-lane PE`

2. **system e2e 优化**
- 在 `v2.8` 中修复 batch 样本边界接收错误
- 将 batch 平均每样本 e2e 压到 `1157261 cycles`
- 约 `23.145 ms @ 50 MHz`

因此当前硬件部分已经形成了：

- SoC 平台
- 数据通路
- 固定模型硬件化
- PE 阵列优化
- e2e 数据流优化
- 板级验证

当前 `k7` 版本补充验证结果为：

- `large_golden`: `1000 / 1000` 通过
- `boundary_cases`: `54 / 54` 通过
- `kernel latency`: `1301 cycles ≈ 26.02 us @ 50 MHz`

对应正式说明见：

- [radar_qmlp_k7_backend_and_validation_2026-04-14.md](/home/soooarr/chipyard/docs/radar_qmlp_k7_backend_and_validation_2026-04-14.md)

这一整条较完整的研究路径。

## 3. 可作为论文“主要工作量”的 4 项内容

下面这些内容更适合作为论文中的“主要完成工作”，因为它们有明确实现对象、系统关系和工程验证基础。

### 3.1 基于 RISC-V 的雷达智能处理 SoC 平台搭建

这一部分包括：

- `Rocket` 软核 CPU 搭建
- `DDR/MIG` 接入
- `TileLink/AXI` 互连对接
- `AXI DMA` 子系统接入
- `UART-TSI` 板级 bring-up

这部分工作量很大，且是后续所有硬件实验的基础。它适合写成论文中的“平台构建与系统实现”部分。

但要注意，**单独把“搭了一个 RISC-V SoC”写成创新点会偏弱**，更适合作为主要工作内容和平台基础。

### 3.2 面向冻结雷达模型的硬件加速器设计与集成

这一部分对应的是：

- 冻结模型 `21 -> 64 -> 32 -> 2 INT8 QMLP`
- `RadarAXISQMLP` 模块设计
- 参数文件与硬件 elaboration 的对接
- QMLP CSR 设计
- 在 `DDR -> MM2S -> QMLP -> S2MM -> DDR` 路径中的集成

这是当前论文硬件部分最核心的一项工作，因为它把“软件模型”真正落到了 SoC 硬件中。

### 3.3 面向 QMLP 的 PE 阵列化与时序友好优化

这一部分对应的是：

- `4-lane PE` 乘加并行结构
- `v2.2 / v2.4 / v2.5` 等版本的演进
- `requant` 路径的结构级优化
- `DSP` 占用变化与 `WNS` 改善

这部分不是简单“把 RTL 改快一点”，而是从固定功能实现进一步推进到可以讲清楚的阵列化结构和实现风格优化。

这也是当前硬件部分最容易形成方法性内容的一项工作。

### 3.4 面向系统端到端性能的数据流优化与板级验证

这一部分对应的是：

- `single-sample` 到 `batch-only` 的路径演进
- `v2.8` 对 batch 样本边界接收的修复
- `e2e` 计时口径建立
- `CPU-only / kernel / system e2e` 三类时延区分

这部分非常重要，因为它把论文从“只做一个算子加速器”推进到“系统级智能处理 SoC”。

从当前结果看：

- `kernel latency ≈ 26.02 us`
- `v2.8 batch per-sample e2e ≈ 23.145 ms`

这已经说明论文里不仅能写“算子优化”，还能写“系统数据流优化”。

## 4. 可作为“创新点候选”的 4 项内容及理由

不是所有完成的工作都适合包装成创新点。下面这些内容更接近可以在论文中讨论的“创新点候选”。

### 4.1 面向冻结雷达特征模型的轻量流式硬件化实现

候选表述方向：

- 面向停车场雷达特征分类任务，提出并实现了一种基于 `AXI-Stream` 数据通路的轻量 `INT8 QMLP` 硬件加速模块。

理由：

- 当前不是通用大模型硬件，而是紧贴任务特征与部署约束
- 模型规模极小，便于与边缘部署、低功耗目标结合
- 已在板级完成闭环验证，不是停留在仿真

适合程度：

- 中等偏上  
- 适合作为“任务驱动的硬件化实现”来写

### 4.2 面向超轻量 MLP 的 4-lane PE 阵列化结构及 requant 优化

候选表述方向：

- 针对小规模 `INT8 QMLP` 的三层全连接计算特征，设计 `4-lane PE` 阵列化结构，并对 requant 常数乘路径进行结构级优化，以改善时序与资源映射。

理由：

- 这一项已经不只是“模型照着写成 RTL”
- 有明确结构设计点：`4-lane PE`
- 有明确优化点：shift-add 替代 DSP 型常数乘
- 有明确结果：`3554 -> 1301 cycles`，`WNS` 明显改善

适合程度：

- 高  
- 这是当前最像“硬件论文方法点”的一项

### 4.3 面向板级部署的 batch 数据流优化机制

候选表述方向：

- 面向边缘 SoC 板级部署场景，设计并验证批处理流式推理机制，通过修正 batch 样本边界接收逻辑与批次级 DMA 调度方式，降低平均每样本端到端时延。

理由：

- 这部分已经不是单纯算法核，而是系统级优化
- 能直接解释为什么 `kernel` 很快但早期 `e2e` 仍然慢
- `v2.8` 已经拿到真实板级结果

适合程度：

- 中高  
- 如果后续再把 `batch8/batch64/noreset` 等路径补齐，这个点会更强

### 4.4 基于 RISC-V SoC 的雷达智能处理软硬件协同部署框架

候选表述方向：

- 构建基于 `RISC-V SoC` 的雷达智能处理软硬件协同部署框架，实现模型、DMA、DDR、加速器和 bare-metal 控制程序的协同集成。

理由：

- 当前工作不是独立 RTL，也不是独立软件，而是明确的 SoC 协同
- 这个点更偏系统集成方法
- 适合作为总贡献之一

适合程度：

- 中等  
- 更适合写成“系统贡献”而非唯一创新点

## 5. 哪些内容更适合作为工程实现工作，而不建议包装成创新点

下面这些内容很重要，但更适合作为工程实现、平台支撑或实验条件，不建议强包装成创新点。

### 5.1 单纯的 Rocket SoC 搭建

原因：

- 基于 Chipyard 搭建 `Rocket + DDR + DMA` 是重要工作，但本身更偏平台实现
- 如果没有和后续雷达任务、加速器、数据流优化结合，仅“搭了一个 RISC-V SoC”创新性偏弱

建议定位：

- 作为论文的系统实现基础

### 5.2 UART-TSI bring-up、独立 ELF 会话排障、自检链清理

原因：

- 这部分工作量很大，也很真实
- 但本质上更偏 bring-up 和调试问题收敛

建议定位：

- 作为工程实现难点与验证过程说明
- 不建议写成核心创新点

### 5.3 单纯的 CSR 扩展、寄存器页映射、脚本封装

原因：

- 这些内容对系统可用性很关键
- 但更多属于工程配套

建议定位：

- 作为实现细节与验证支撑

### 5.4 单次频率 sweep 或零散时序修补

原因：

- 频率 sweep、PLL 兼容、时序违规排查很重要
- 但它们更像优化过程，不适合直接上升为创新点

建议定位：

- 作为实现迭代过程和工程难点说明

## 6. 硬件部分在论文中的建议章节组织方式

建议硬件部分不要写成“模块清单式说明”，而是写成“平台 -> 加速器 -> 优化 -> 验证”这条主线。

### 建议章节组织

#### 第 3 章 系统总体架构设计

可包含：

- 系统需求与部署目标
- 软硬件协同总体框图
- SoC 顶层结构
- 数据通路与控制通路划分
- 时钟与存储组织

这一章主要解决：

- 为什么要用 `RISC-V SoC`
- 系统整体长什么样
- CPU、DDR、DMA、加速器各自负责什么

#### 第 4 章 雷达信号智能处理硬件实现

可包含：

- 冻结模型的硬件映射关系
- `RadarAXISQMLP` 结构设计
- 参数读取与量化实现方式
- `L1/L2/L3` 的计算流程
- CSR 与接口说明

这一章主要解决：

- 模型是怎么变成硬件的
- 计算、输入输出和控制是怎么组织的

#### 第 5 章 加速器优化与系统级数据流优化

可包含：

- baseline 与 `4-lane PE` 结构对比
- requant 路径优化
- batch e2e 优化
- `kernel latency` 与 `system e2e latency` 的区分

这一章主要解决：

- 为什么要继续优化
- 优化点具体在哪里
- 优化带来了什么效果

#### 第 6 章 硬件验证与性能评估

可包含：

- 板级验证方法
- 多样本对拍
- `CPU-only`、`kernel`、`e2e` 对比
- 资源占用
- 时序结果
- 频率与稳定性边界

这一章主要解决：

- 硬件是不是正确
- 加速效果到底怎样
- 系统目前的瓶颈在哪里

## 7. 硬件主线如何与软件模型主线衔接

硬件和软件两条线在论文里不能平行堆叠，必须围绕同一个问题来收口。

当前比较合适的衔接方式是：

### 7.1 软件主线负责回答

- 为什么停车场雷达任务适合这种输入表示
- 为什么冻结模型选择 `21 -> 64 -> 32 -> 2 INT8 QMLP`
- 模型精度、参数量和量化结果如何

### 7.2 硬件主线负责回答

- 这个模型如何落到 `RISC-V SoC`
- 如何通过 `DDR + DMA + AXIS + QMLP` 跑通
- 如何通过 `PE` 阵列与数据流优化降低时延

### 7.3 两条线汇合的关键接口

两条线汇合的地方建议明确为：

1. **冻结模型 handoff**
- 输入维度
- 权重
- 偏置
- scale
- golden 数据

2. **部署目标一致**
- 低功耗
- 边缘端
- 停车场雷达目标检测/分类场景

3. **统一评价口径**
- 参数量
- 精度
- `CPU-only`
- `hardware kernel`
- `system e2e`

最推荐的论文主线是：

- 软件部分证明：模型足够小且精度可用
- 硬件部分证明：模型可以在 `RISC-V SoC` 上高效落地并获得加速

这样整篇论文会自然收敛到：

- **面向停车场雷达边缘部署的软硬件协同智能处理系统**

## 10. 当前最推荐的写作策略

对于硬件部分，当前最推荐的写法是：

1. **先把“系统搭起来”讲清楚**
- RISC-V SoC
- DDR/DMA/AXIS
- 为什么这样搭

2. **再把“模型怎么落硬件”讲清楚**
- QMLP
- 参数读取
- 输入输出
- 数据通路

3. **再把“为什么要优化”讲清楚**
- baseline 太慢在哪里
- `PE` 为什么能降 kernel
- batch 为什么能降 e2e

4. **最后用板级结果收口**
- 正确性
- 时延
- 资源
- 时序

这样能避免论文硬件部分写成：

- 零散堆模块
- 或只剩调试笔记

而是收敛成一条完整的研究主线。
